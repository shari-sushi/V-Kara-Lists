# DB再設計: 動画(videos)と歌唱(video_songs)の統一モデル

## 背景・目的

Issue #398。旧 #225 では「1動画複数曲(multiple_songs_movies)」「1動画1曲(single_song_movies)」の2テーブル分割案だったが、非対称構造（multipleは動画+子テーブルの2階層、singleは1行に同居）でお気に入り・検索・型定義がすべて2パターン分岐し、コンテンツ種別（歌枠・ライブ・オリ曲・歌ってみた）が増えるたびに破綻する。

→「動画(videos)」と「その中の歌唱(video_songs)」の2テーブルに統一し、4種の違いは `videos.category`(tinyint) の値だけで表現する。単曲でも歌唱行を必ず1件作り、全コンテンツを完全同形にする。

検討して採用しなかった代替案とその理由は `V-Kara-Lists.wiki/設計判断ログ.md` を参照。

## スキーマ

### videos

| column | 型 | 備考 |
| --- | --- | --- |
| id | INT PK AUTO_INCREMENT | 旧 movie_url PK を廃止 |
| category | TINYINT NOT NULL | 11:オリ曲 12:歌ってみた 31:歌枠 32:ライブ（10/30は大分類予約） |
| movie_url | VARCHAR(100) UNIQUE NOT NULL | YouTube URL |
| title | VARCHAR(200) NOT NULL | |
| vtuber_id | INT NOT NULL | FK→vtubers |
| published_at | DATETIME NULL | 動画公開日（任意） |
| inputter_id | INT NOT NULL | |
| created_at / updated_at | DATETIME | |

### video_songs（現行karaokesの正規化版）

| column | 型 | 備考 |
| --- | --- | --- |
| id | INT PK AUTO_INCREMENT | |
| video_id | INT NOT NULL | FK→videos |
| sing_start | TIME NOT NULL | 歌枠/ライブは実際の開始時刻。**単曲(11/12)はNULLではなく固定センチネル値`'00:00:00'`を入れる**（MySQLのUNIQUE制約はNULL同士を別物扱いするため、NULLのままでは単曲の重複作成を防げない） |
| song_name | VARCHAR(100) NOT NULL | |
| inputter_id | INT NOT NULL | |
| created_at / updated_at | DATETIME | |
| UNIQUE(video_id, sing_start) | | |

`song_id`（将来の曲マスタ #352 用）は今回は追加しない。#352実装時にALTER TABLEで追加する。

### favorite_videos / favorite_video_songs

video/video_songsは対象の粒度が異なる（配信全体が好き／配信内の1曲が好き、はどちらも起こりうる）ため、`target_type`によるポリモーフィック関連ではなくテーブルを分けて実FKを張る。

```sql
favorite_videos (
  id, listener_id, video_id (FK→videos), created_at,
  UNIQUE(listener_id, video_id)
)
favorite_video_songs (
  id, listener_id, video_song_id (FK→video_songs), created_at,
  UNIQUE(listener_id, video_song_id)
)
```

deleted_atは付けない。

## データ移行

旧`original_songs`はコード上、作成処理(`CreateOriginalSong`相当)が存在せず実データ0件のため移行対象外。実質的な移行対象は歌枠(31)のみ（`movies`+`karaokes`+`favorites`）。

```sql
TRUNCATE videos; TRUNCATE video_songs; TRUNCATE favorite_videos; TRUNCATE favorite_video_songs;

-- movies → videos（歌枠=31のみ。旧movies/karaokesにcreated_atが無いため移行時刻で埋める）
INSERT INTO videos (category, movie_url, title, vtuber_id, inputter_id, created_at, updated_at)
SELECT 31, movie_url, movie_title, vtuber_id, movie_inputter_id, NOW(), NOW()
FROM movies;

-- karaokes → video_songs
INSERT INTO video_songs (video_id, sing_start, song_name, inputter_id, created_at, updated_at)
SELECT v.id, k.sing_start, k.song_name, k.karaoke_inputter_id, NOW(), NOW()
FROM karaokes k
JOIN videos v ON v.movie_url = k.movie_url;

-- favorites（動画のみ、karaoke_id=0） → favorite_videos
INSERT INTO favorite_videos (listener_id, video_id, created_at)
SELECT f.listener_id, v.id, NOW()
FROM favorites f
JOIN videos v ON v.movie_url = f.movie_url
WHERE f.karaoke_id = 0;

-- favorites（karaoke指定） → favorite_video_songs（movie_url+sing_startの自然キーでjoin。IDは新規採番のため一致しない）
INSERT INTO favorite_video_songs (listener_id, video_song_id, created_at)
SELECT f.listener_id, vs.id, NOW()
FROM favorites f
JOIN karaokes k ON k.karaoke_id = f.karaoke_id
JOIN videos v ON v.movie_url = k.movie_url
JOIN video_songs vs ON vs.video_id = v.id AND vs.sing_start = k.sing_start
WHERE f.karaoke_id != 0;
```

## 実装ステップ

1. gorm struct（Video, VideoSong, FavoriteVideo, FavoriteVideoSong）を作成し、AutoMigrateで新テーブル生成（ローカルDocker DB）
2. backendをロジック面で移行（repository → service → handler の順、型情報一新）
3. frontendを移行（型一新 / topに「開発中」表示 / 4コンテンツ仮ページ）
4. localで動作確認。上記データ移行SQLをローカルDBに対して試し、旧→新のデータコピーが正しいか検証
5. **（要人手確認・本番作業）** EC2でCREATE TABLE（新テーブルのみ追加、旧テーブルは無傷）。本番はまだ旧スキーマで稼働
6. **（要人手確認・本番作業）** リリース: RDSバックアップ取得 → サービス一時停止 → データ移行SQL実行 → api/appデプロイ → 再開。旧テーブルは`_old`にリネームして一定期間保持（即DROPしない）

ステップ5・6は本番DB・サービス停止を伴うため、実装(1〜4)が完了しビルド/テストが通った段階で一度レビューを挟み、人手で実施する。

## 注意事項

- 個人利用アプリのため超破壊的変更を許容（旧movie_url PK廃止、favorites作り直し）
- カラム削除・型変更はAutoMigrateでは反映されない → 本番は手動ALTER。本番移行前にバックアップ必須
- ライブ(32)・歌ってみた(12)は既存データ無し。移行対象は歌枠(31)のみ（オリ曲(11)も`original_songs`未実装のため実データ無し）
- `video_songs.id`は旧`karaoke_id`と値を一致させない（URL等に露出しておらず一致させる実益が無いため）。favoritesの移行は自然キー(movie_url+sing_start)でjoinする
- 主キーはUUIDにせず、既存の他エンティティと同様INT AUTO_INCREMENTを継続する
- お気に入りの振る舞い（いいねする等のロジック）はVideo/VideoSongドメイン構造体に持たせず、従来通りservice層に置く（domain層はデータ構造体のみという既存方針を維持）
- 実装中に新たに却下した設計案が出たら `V-Kara-Lists.wiki/設計判断ログ.md` に追記する
