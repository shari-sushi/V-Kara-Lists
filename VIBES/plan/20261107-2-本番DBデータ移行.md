# 本番DBデータ移行（#398 の残り）

## 背景・目的

PR #414（2026-08-09 マージ）で DB を videos / video_songs / favorite_videos / favorite_video_songs の統一モデルに変更したが、本番のデータ移行（計画 `VIBES/done/20260625-1-DB再設計-動画と歌唱の統一モデル.md` のステップ5・6）が残っている。

2026-11-07 時点の状況（統括セッションの調査）:

- #414 以降、deploy.yml の EC2 への SSM ステップが毎回失敗しており、本番は #414 より前の旧コードで動いている（公開 API は旧形式。karaokes 574 / movies 76 / vtubers 24）
- そのため本番の新テーブルは未作成の見込み（新 api が一度も起動していない）。AWS 認証の設定後に `398_inspect.sql` で確定させる
- ECR の `latest` はすでに新コード。デプロイが直った瞬間に新コードが未移行の DB に出るので、デプロイの修正とこの移行はセットで行う

この PR では、本番作業を安全に行うためのスクリプト・SQL・runbook を用意する。本番の操作はユーザーが手で行う。

## 変更スコープ

- `scripts/db/sql/` - 状態確認・新テーブル作成・移行・検証・旧テーブルのリネーム（と取り消し）の SQL
- `scripts/db/backup-on-ec2.sh` - EC2 上での手動バックアップ（mysqldump → S3 `manual/<ラベル>/`）
- `scripts/db/rehearse-local.sh` と `scripts/db/rehearsal/` - 使い捨て MySQL コンテナでのリハーサル（架空データまたは本番ダンプ）
- `docs/db-migration-398.md` - 本番 runbook（メンテ開始 → バックアップ → 移行 → 検証 → デプロイ → 確認 → 再開、ロールバック）
- アプリのコード（t0016Go / t0016Next）は変更しない

## 既存の移行 SQL からの変更点

| 変更 | 理由 |
| --- | --- |
| TRUNCATE + INSERT をやめ、自然キーで `NOT EXISTS` を判定する差分マージにした | 新コードが先に出て新テーブルにデータが入っていても消さない。再実行しても増えない |
| 新テーブルの作成を api の起動から切り離した（`398_create_new_tables.sql`） | 移行前に新 api を公開しないため。AutoMigrate と同じ定義であることを検証済み（下記） |
| 旧 favorites の論理削除済み（`deleted_at IS NOT NULL`）を除外した | 旧 Favorite は `gorm.Model` で、解除済みのお気に入りが論理削除で残っている。既存 SQL では復活してしまう |
| 動画お気に入りの条件を `karaoke_id = 0` から `COALESCE(karaoke_id, 0) = 0` にし、重複は1件にまとめる | 旧 `karaoke_id` 列は NULL を許容しており、NULL の行が漏れる |
| お気に入りの `created_at` を旧データから引き継ぐ（無ければ移行時刻） | 旧 favorites には created_at がある。旧 movies / karaokes には無いので移行時刻で埋める（既存方針どおり） |
| 旧 karaokes の NULL 列（sing_start / song_name / inputter）の行は移行しない | 新テーブルでは NOT NULL。件数は `398_inspect.sql` で事前に出す |
| 新側で同じ URL が歌枠以外として登録済みなら、旧 karaokes を付け替えない | 単曲は歌唱行1件、という不変条件を守る |
| 移行全体を1トランザクションにした | 途中失敗で中途半端なデータを残さない |

## 実装ステップ

1. 旧スキーマ（`66d7f2c^` の domain）と新スキーマを、本番と同じ順（旧 AutoMigrate → 新 AutoMigrate）でローカルに作り、実際の DDL を取得する（完了）
2. SQL・バックアップ・リハーサルのスクリプトを作る（完了）
3. ローカルで検証する（完了）
   - `rehearse-local.sh fixture`（新テーブルなし）: 想定どおり 3/5/1/1 件、再実行で増えない、リネームと取り消しが通る
   - `rehearse-local.sh fixture-post-deploy`（新テーブルに先行データあり）: 想定どおり 4/7/2/1 件、既存データを保持
   - `backup-on-ec2.sh` を使い捨てコンテナと aws のダミーで実行し、そのダンプで `rehearse-local.sh dump` が通る
   - `398_create_new_tables.sql` で作ったテーブルと AutoMigrate が作るテーブルを information_schema で比較し、列・インデックス・照合順序が一致。その上で新コードの AutoMigrate を実行してもスキーマが変わらない
4. （ユーザー）AWS 認証を設定し、`398_inspect.sql` で本番の状態を確定させる
5. （ユーザー）本番のバックアップで `rehearse-local.sh dump` を実行する
6. （ユーザー）デプロイ失敗の原因修正と合わせて、runbook どおりに本番作業を行う
7. （ユーザー、1〜2週間後）旧テーブルを `_old` にリネームする

## migration ツールの導入について（提案。導入は合意後に別 PR）

| 案 | 良い点 | 気になる点 |
| --- | --- | --- |
| GORM AutoMigrate を続ける（今の方式） | 追加の仕組みが要らない | 列の削除・変更・データ移行ができない。履歴が残らず、今回のように「本番がどこまで進んだか」が DB から分からない |
| AutoMigrate + 番号付き手動 SQL（この PR の方式） | 今すぐ使える。データ移行やリネームを SQL ファイルとレビューで管理できる | 適用済みかどうかを記録する表が無く、人が runbook で管理する |
| goose | SQL と Go 関数の両方で書ける。`goose_db_version` 表で適用状況が残る。CLI が単純 | 導入時に既存テーブルの初期スキーマを作る必要がある |
| golang-migrate | 利用者が多い。up/down の SQL ファイルだけで単純 | Go 関数での移行は書けない |
| Atlas | GORM の構造体から差分 SQL を自動生成できる | 仕組みが大きい。個人規模のアプリには重い |

提案: 当面はこの PR の「AutoMigrate + 番号付き手動 SQL」で進め、Go のバージョンアップ（go.mod は 1.18）の後に goose を入れる。goose と golang-migrate の最新版が要求する Go のバージョンは導入時に確認する。

## 注意事項

- 本番 EC2 のディスクは空きが約 360MB で、新旧の api/app イメージを同時に置けない。runbook では旧コンテナとイメージを削除してから新イメージを pull する。旧イメージに戻すときは ECR の旧 sha タグを pull し直す
- MySQL のメモリ調整は、このリリースとは別のブランチ（`perf/mysql-memory-tuning`）で行う
- public リポジトリのため、本番ダンプ・ホスト名・IP・バケット名・DB の認証情報はコミットしない。ダンプは S3 とリポジトリ外（例: `~/v-kara-backups/`）にだけ置き、`rehearse-local.sh` はリポジトリ内のダンプを拒否する
- DB の認証情報はスクリプトに書かず、コンテナ内の環境変数（db.env 由来）を使う
- 本番の docker volume を消す操作（`down -v`）や DROP はこの作業では行わない
- 新コードの domain は「実FK」と書いているが、構造体に関連定義が無いため AutoMigrate は外部キーを作っていない。この PR では変更しない（必要なら別 issue）
- 新 Follow 構造体は `gorm.Model` を外したが、本番の follows には `deleted_at` 列が残る。Follow は現在どこからも使われていないので影響は無いが、使い始めるときは論理削除済みの行の扱いに注意する
