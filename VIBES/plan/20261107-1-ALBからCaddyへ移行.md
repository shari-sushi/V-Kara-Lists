# ALB から Caddy へ移行（#372）

## 背景・目的

ALB（`v-kara-ec2-unified-alb`）は固定費がかかるが、構成は EC2 1台・TG 2つで、ロードバランシングは使っていない。TLS 終端とホスト名による振り分けだけを EC2 上の Caddy に移して ALB を廃止し、コストを下げる。

## 現状（2026-11-07 調査）

- DNS は Cloudflare のプロキシ経由（`v-karaoke.com` と `backend.v-karaoke.com` は両方とも Cloudflare の IP、`server: cloudflare`）
- ALB の構成は `infra/terraform/alb.tf` に listener と rule も含めて定義済み（実機と一致しているかは未確認）
  - HTTPS:443（ACM `*.v-karaoke.com`）: デフォルトは app TG（EC2:80）。host が `backend.v-karaoke.com` なら api TG（EC2:8080）
  - HTTP:80: `app_to_http` TG（EC2:80 に **HTTPS** で転送）。EC2:80 は平文 HTTP なので失敗する。実際に `http://v-karaoke.com` は 502 を返す（既存の不具合）
- フロントの API 呼び出し先は `t0016Next/myapp/env.ts` にハードコードされた `https://backend.v-karaoke.com/v1`
- Go 側: CORS は `v-karaoke.com` を許可。Cookie は `Domain=v-karaoke.com; Secure; SameSite=Lax`。ホスト名を変えないので影響はない
- `https://` は正常に応答している → Cloudflare の SSL モードは Full か Full(strict)（どちらかは未確認）
- EC2 は `associate_public_ip_address = true` で、EIP は無い（IaC 上）。インスタンスタイプは IaC 上 t3a.micro（実機は未確認）
- EC2 の SG は ALB SG からの 80/8080 と SSH のみ許可

## TLS 方式の比較

| | (a) Origin Certificate + Full(strict) | (b) Caddy ACME HTTP-01 | (c) ACME DNS-01（CF API トークン） |
| --- | --- | --- | --- |
| 証明書 | Cloudflare 発行、最長15年 | Let's Encrypt、90日で自動更新 | Let's Encrypt、90日で自動更新 |
| SG を Cloudflare の IP のみに絞れるか | 可 | 実質不可（LE からの :80 到達が必要。プロキシ経由でも動くが、Always Use HTTPS やリダイレクト設定と干渉しやすい） | 可 |
| サーバ上の秘密情報 | 証明書の秘密鍵のみ | なし（自動生成） | **ゾーンを編集できる API トークン**（漏れたときの影響が大きい） |
| Caddy イメージ | 公式イメージのまま | 公式イメージのまま | `caddy-dns/cloudflare` を含むカスタムビルドが必要（ECR とビルドの手間が増える） |
| 更新失敗のリスク | ほぼ無し（15年） | 更新失敗で証明書が切れる | トークン失効で更新失敗 |
| Cloudflare 以外からの直アクセス | 証明書が公開 CA ではないため不可（副次的な防御） | 可 | 可 |
| Cloudflare をやめるとき | 証明書の差し替えが必要 | そのまま使える | そのまま使える |

**推奨: (a)**。ACME への依存も API トークンも不要で、SG を Cloudflare の IP に絞る方針と矛盾しない。Cloudflare をやめる予定は無い前提。任意で Authenticated Origin Pulls（mTLS）を後から追加できる。

### 秘密情報の置き場所

- Origin Certificate（`origin.pem`）と秘密鍵（`origin.key`）を、既存の env と同じように S3 に置く（例: API env バケットの `caddy/origin.pem` と `caddy/origin.key`）
- 現在の IAM ポリシー `policy_get_s3` は `/.env` しか GetObject を許可していない → `infra/terraform/ec2.tf` に 2 オブジェクト分の許可を追加する
- deploy.yml と `scripts/ec2/get_env_files_from_s3.bash` で `/home/ubuntu/v-kara/caddy/certs/` に取得し、`chmod 600`。Caddy コンテナには読み取り専用でマウントする
- リポジトリにはパスとプレースホルダのみを書く

## 変更スコープ

- `ec2-docker-compose.yml`: `caddy` サービスを追加（`caddy:2.x` の固定タグ、ports 80/443、`caddy_data` と `caddy_config` の volume、Caddyfile と certs を ro マウント）。app のホスト側 :80 公開をやめる。8080 は移行期間中だけ残す（後述）
- `infra/caddy/Caddyfile`（新規）
  - `https://v-karaoke.com` → `app:80`、`https://backend.v-karaoke.com` → `api:8080`。どちらも `tls /certs/origin.pem /certs/origin.key`
  - `:80` のキャッチオール ブロックで、ホスト名を問わず `app:80` にプロキシする。ALB のヘルスチェックは Host が「ターゲットの IP:ポート」になるため、ホスト名指定のブロックだけでは応答できず、TG が unhealthy になる
  - グローバル設定 `auto_https disable_redirects` で、Caddy 側の HTTP→HTTPS リダイレクトを止める（移行期間中の ALB→EC2:80 の経路でループさせないため。リダイレクトは Cloudflare の Always Use HTTPS に任せる）
  - `trusted_proxies static` に Cloudflare の IP レンジを列挙する（プラグイン不要）。出典と更新手順は runbook に書く
- `.github/workflows/deploy.yml`
  - Caddyfile を EC2 に配置する（compose と同じく raw GitHub から取得）。Caddyfile の変更も検知対象に加える
  - S3 から証明書を取得する。`rm` の対象からは外す（Caddy の再起動や reload のときに必要なため）。`chmod 600` と ro マウントで保護する
  - compose が変わったときの再起動対象に `caddy` を追加する
  - ヘルスチェックを Caddy 経由に変更する: `curl -sfk --resolve v-karaoke.com:443:127.0.0.1 https://v-karaoke.com/user/signin`、`backend.v-karaoke.com` の `/health` も同様に確認する
- `scripts/ec2/get_env_files_from_s3.bash`: 証明書の取得を追加する
- `infra/terraform/`: IAM の S3 許可を追加。EIP を追加。SG（80/443 は Cloudflare の IP のみ）。ALB 系は切替が安定してから別 PR で削除
- `docs/caddy-migration-runbook.md`: 切替 runbook

## 実装ステップ

1. （ユーザー）読み取り確認: `aws login` 後に、instance type、ALB の listener と rule の実機、EC2 の EIP の有無を確認する。Cloudflare の SSL モードはダッシュボードで確認してもらう
2. Caddyfile と compose を実装し、ローカルで自己署名の証明書（または `tls internal`）を使って HTTP と HTTPS の疎通を確認する（`--resolve` で両ホスト名）
3. deploy.yml と S3 取得スクリプトを修正する
4. Terraform（IAM、EIP、SG）の差分を作り、`terraform plan` 用の手順を runbook にまとめる（apply はユーザーが行う）
5. runbook を作成する
6. PR（ユーザーの承認後に push）

## 本番切替 runbook（概要、詳細は `docs/caddy-migration-runbook.md`）

ダウンタイムをゼロにするために段階的に進める。

前提: **#398 の本番リリースが完了していること**。本番デプロイは #414 以降失敗しており、ECR の api:latest にはすでに #398 の新コードが入っている。この PR は compose を変更するので、デプロイすると api が pull される。そのため、本番に出す順番は「デプロイの修正 → DB 移行のリリース → Caddy」にする。また、EC2 の SG の 80/8080 が ALB SG からのみ許可されていること（移行期間中は 8080 のホスト公開が残るため）。

1. Cloudflare で Origin Certificate を発行する（`v-karaoke.com`, `*.v-karaoke.com`）。S3 に配置する
2. Terraform で IAM 許可と EIP を apply し、EIP を EC2 に関連付ける（public IP が変わるが、DNS は ALB を向いているので影響は無い）
3. PR をマージ → deploy。Caddy が :80/:443 で起動する。ALB からの経路（EC2:80 → Caddy → app、EC2:8080 → api）はそのまま動くので、サイトは止まらない
4. SG に 443 を追加（Cloudflare の IPv4 レンジのみ）。EC2 上で `curl --resolve` を使い、EIP 経由の HTTPS を確認する
5. Cloudflare の SSL モードを Full(strict) にする（まだなっていなければ）。Always Use HTTPS を ON にする（現在の HTTP 502 も解消される）
6. Cloudflare の DNS: `v-karaoke.com` と `backend.v-karaoke.com` を ALB の CNAME から A `<EIP>`（Proxied）に変更する
7. 確認: トップページ、ログイン（Cookie）、API、Caddy のログに ALB 以外のアクセスが流れているか
8. 数日様子を見て、ALB、TG、listener を削除する（Terraform から削除する PR）。ACM 証明書は prevent_destroy なので残すか別途判断する。compose から 8080 のホスト公開を外す。SG から ALB 系のルールを外す

### ロールバック

- 手順 6 の後に問題が出た場合: Cloudflare の DNS を ALB の CNAME に戻すだけでよい（ALB と TG は削除せずに残してあるため即時に戻る）
- 手順 3 の後に Caddy が原因で ALB 経路が壊れた場合: 直前のコミットに戻して deploy（または EC2 上で `docker-compose stop caddy` し、app のポートを戻した compose で `up -d`）

## 外形監視

- UptimeRobot（無料枠: 5分間隔、50モニタ）で `https://v-karaoke.com/user/signin` と `https://backend.v-karaoke.com/health` を監視する。通知先はメールか Discord
- 代替: Cloudflare Health Checks（有料プラン）、GitHub Actions の cron（無料だが最短5分で遅延がある）

## 注意事項

- t3a.micro（メモリ 1GB）。Caddy の常駐メモリは数十MB 程度で影響は小さいが、切替後に `docker stats` で確認する
- セッションC（DB 移行）も compose と deploy を変更する予定。本番作業は Caddy が先、DB が後
- public リポジトリ: EIP、アカウントID、zone ID、証明書と秘密鍵、S3 バケット名はコミットしない
- Cloudflare の IP レンジは変わることがある。SG の更新手順を runbook に書く
