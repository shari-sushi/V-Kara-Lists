# service層テスト追加

## 背景・目的

リファクタリングの一環として、service層にユニットテストを追加する。 `repository/interface.go` にインターフェースが定義済みなので、モックを自作することで DB なしにテストが書ける。

## 変更スコープ

新規ファイル:

- `t0016Go/service/content_service_test.go`
- `t0016Go/service/activity_service_test.go`

既存ファイルへの変更: なし

## テスト対象の選定方針

Repositoryに委譲するだけのメソッドはテスト価値が低い。 **ビジネスロジックを持つメソッドを優先する。**

### ContentService（高優先度）

`CreateVtuber` / `CreateMovie` / `CreateKaraokes` の3メソッドは `Normalize → Validate → Repository.Create` の流れを持つため、以下を検証できる:

- バリデーションエラー時にRepositoryが呼ばれないこと
- 正規化（TrimSpace等）が実行されること
- 正常時はRepositoryに処理が委譲されること

### ActivityService（中優先度）

`CreateMovieFavorite` / `DeleteMovieFavorite` / `UpdateMovieFavorite` は `fav.KaraokeId = 0` の保護処理を持つ。混入したKaraokeIdが0にリセットされることを検証する。

`FindEachRecordsCreatedByListenerId` はエラーを集約する独自ロジックを持つ。一部のRepositoryが失敗してもパニックせず、errsにエラーが追加されることを検証する。

## 実装ステップ

1. `content_service_test.go` を作成
   - `mockContentRepo` 構造体（ContentRepositoryを実装）を定義
   - `TestContentService_CreateVtuber`（正常・バリデーション失敗・正規化）
   - `TestContentService_CreateMovie`（正常・Repositoryエラー時）
   - `TestContentService_CreateKaraokes`（正常・バリデーション失敗・空スライス）

2. `activity_service_test.go` を作成
   - `mockFavoriteRepo` 構造体（FavoriteRepositoryを実装）を定義
   - `TestActivityService_CreateMovieFavorite`（KaraokeIdが0にリセットされること）
   - `TestActivityService_FindEachRecordsCreatedByListenerId`（エラー集約ロジック）

## 完了条件

- [ ] `go test ./service/...` がパスする
- [ ] `go vet ./service/...` がパスする
- [ ] テストが実際のビジネスロジックを検証していること（常にtrueのテストでない）

## 注意事項

- モック構造体はテストファイル内にのみ定義する（`service/` パッケージ外に出さない）
- Repository インターフェースのメソッドを全てスタブ実装する必要があるため、未使用メソッドは `panic("not implemented")` で実装する
- `common.GetGuestListenerID()` の戻り値によって `ValidateKaraoke` の分岐が変わることに注意
