# セルフレビュー（3段階 → 先回りPR）

現在の変更を、過去に受けた指摘を繰り返さず・レビューで無駄な質問が出ない状態まで仕上げる。
補足（あれば）: $ARGUMENTS

## 全体の流れ

次の **3段階** を順に行う。**各段階で問題点が見つかったら、その場で修正し、段階1から再度やり直す**
（修正によって新たな綻びが生まれていないかを毎回頭から点検するため）。

1. 段階1: セルフレビュー（過去フィードバックを活かした観点での点検）
2. 段階2: レビューアが質問・指摘しそうな観点でのレビュー
3. 段階3: 命名の誤りがないかのレビュー

3段階すべてを「問題なし」で通過したら:

- 段階4 / PR作成: レビューで無駄な指摘・質問が減るよう、トレードオフや仕様の判断を本文に明記して PR を出す
- 段階5 / 先回り再確認: そのコミット・PR が「指摘に先回りできている」か再確認し、足りなければ追加コミット。問題なければ終了。

## 事前準備（毎回の起点）

段階1に入る前（およびやり直しのたび）に必ず行う:

- `git branch --show-current` で作業ブランチを確認（意図したブランチか）
- `git --no-pager diff develop...HEAD` と `git --no-pager status -sb` で、コミット済み + 未コミットの両方を対象にする
- PR がある場合は `gh pr view` で説明文も読む（段階1の「明文化チェック」で使う）
- 過去の教訓を読み込む:
  - `.claude/feedback/log.md`（過去に受けた個別の指摘）
  - `.claude/feedback/lessons.md`（蒸留済みの教訓）

## 段階1: セルフレビュー

### fresh-eyes でレビューする（重要）

**コードを書いた文脈のまま自己レビューすると同じ思い込みを持ち越して見逃す。**
変更が自分の手によるものなら、`Agent`（`code-reviewer` 等のレビュー用、無ければ `Explore`）に
**クリーンな文脈で**差分レビューを依頼し、その指摘を取り込む。差分が小さい/自明な場合のみ自分で実施してよい。

### チェックリスト（feedback/lessons で貯めた知見）

過去の指摘から特に以下を重点的に見る（log.md の蓄積に応じて随時追加）:

- [ ] **値と型のソース一致**: 特定の値を代入するフィールドの型注釈が、生の `number`/`string` ではなく元の型/enum になっているか。値と型の出所が食い違っていないか。
- [ ] **既存パターンとの一貫性**: 同種の処理が既にある場合、その流儀（エラーハンドリング・型定義の置き場所・deps の作り方・3層アーキの責務分離等）に揃っているか。差分内の論理が正しくても、既存の流儀とズレると不整合になる。
- [ ] **新エンドポイントは「正しい peer ファミリ」の横断ガードを全部引き継ぐ**: 新しい API/ハンドラを足したら、(1) 比較対象を**同じ actor／認証モデルの peer** に正す（たまたま開いた“似た”兄弟を踏襲しない）。(2) その peer が一律で持つ横断的な認可ガード（JWT 認証・所有者チェック・利用停止チェック等）を全部引き継いだか列挙して照合する。(3) ガードを省くなら**理由コメントを必ず添える**（無言の欠落は authz バイパス）。
- [ ] **correctness**: 分岐の網羅、失敗時の挙動、非同期処理（goroutine / Promise）の順序と例外・エラー伝播。エラーを握りつぶしていないか（`_ = err` 禁止）。
- [ ] **共有 state の書き手を全部数える**: ある state（キャッシュ・グローバル変数・同じ DB レコード等）を新たに上書き／再取得する変更を入れたら、その state を書く他の経路（楽観更新、fire-and-forget の保存、別 effect・別ハンドラ・別ルート）を列挙し、競合を点検する。
- [ ] **「後で回復/再実行する」の主張はトリガを裏取り**: コメントや握りつぶしの根拠に「次の○○で再取得される／回復する」と書くなら、その再実行を起こす具体的トリガが実在するか確認する。
- [ ] **同じ不変条件の二重実装**: 非自明な不変条件が2箇所以上に現れたらヘルパーへ集約する。自分の修正で既存ロジックを手書きコピーしていないか、「直した結果」にも一貫性 lens を当てる。
- [ ] **taint（ユーザー入力 → 外部シンク）**: ユーザー制御の文字列を新しい外部シンク（SQL・HTML/テンプレート・シェル・ログ・外部API本文）へ流していないか。スコープは「diff の追加行」ではなく「触れた経路に流れる全入力」。
  - SQL は文字列連結せず GORM のプレースホルダ（`Where("col = ?", v)`）を使う。HTML は生注入（`dangerouslySetInnerHTML` 等）を避ける。
  - 敵対的入力ケース（`name="<script>..."` 等）のテストを1件足せているか。
  - public 出力は internal/認証済み出力より危険度が高いので優先する。「既存に合わせる」一貫性 lens はここでは逆効果になりうる。
- [ ] **規約**: `.claude/rules/coding-standards.md` 準拠。`any` 禁止（TS）、相対パス禁止（`@/` 使用）、ドメイン層に Gin/GORM を import しない（Go）。
- [ ] **lint / build / test**: 触れた範囲に応じて以下が通るか（完了の必須項目）。
  - Frontend: `cd t0016Next/myapp && npm run lint && npm run build`
  - Backend: `cd t0016Go && go build ./... && go vet ./... && go test ./...`

### 明文化チェック（不要な再指摘を防ぐ）

実装時にあえて選んだトレードオフ（処理順序・設計の非対称・あえて修正しなかった既知のリスク等）を洗い出し、
**その根拠が PR 説明文 or コードコメントに書かれているか**を確認する。書かれていなければ段階4の PR 本文に盛り込む。

> ここで問題が見つかったら **修正 → 事前準備からやり直し**。問題なしなら段階2へ。

## 段階2: レビューアが質問・指摘しそうな観点でのレビュー

「自分がこの PR のレビューアなら、どこで手を止めて質問するか」を想像して洗い出す:

- なぜこの実装方法を選んだのか（他の自然な選択肢を退けた理由が読み取れるか）
- この分岐・この値・このマジックナンバーの意図は？ 境界条件は意図通りか
- ここはあえて変えていない／あえて対応していないが、それは意図的か漏れか
- エラー時・空配列・null・上限超過などの端ケースはどう振る舞うか
- 影響範囲: この変更で壊れうる既存機能・呼び出し元はないか

→ 「質問されそう」と感じた点は、コードコメント or PR 本文で先回りして答えられる状態にする。

> ここで問題（説明不足・想定漏れ・実装の綻び）が見つかったら **修正/明文化 → 事前準備からやり直し**。問題なしなら段階3へ。

## 段階3: 命名の誤りがないかのレビュー

差分で導入・変更した名前を洗い出し、誤りがないか点検する:

- 変数・関数・型・ファイル名が**実際の中身/責務と一致**しているか（嘘の名前になっていないか）
- 命名規則準拠（`.claude/rules/coding-standards.md`）:
  - TS: ファイルは PascalCase（コンポーネント）/ camelCase（その他）、型は PascalCase、関数/変数は camelCase、定数は UPPER_SNAKE_CASE
  - Go: ファイルは snake_case、型/公開関数は PascalCase、非公開関数/変数は camelCase
- 既存の同種の名前と語彙・粒度が揃っているか（同じ概念に別語、別概念に同語を使っていないか）
- スペルミス・和製英語・複数形/単数形の不整合・boolean の `is`/`has` 等の接頭辞
- コメント内の具体値（クラス名・数値・しきい値・カラム名）がコード本文と1文字単位で一致しているか。値に言及不要なら数値を書かない。

> ここで問題が見つかったら **修正 → 事前準備からやり直し**。問題なしなら段階4へ。

## 段階4: 先回りPRの作成

3段階すべてを通過したら PR を出す（既存 PR があれば本文を更新）。
**目的は「レビューで無駄な指摘・質問が出ない」こと。**

PR 本文に必ず含める:

- **issue 運用**: PR 本文の1行目に `- close #{対応issue番号}` を記載する（`.claude/rules/overview.md` の規約）
- **何を・なぜ**: 変更の概要と背景（解決する課題）
- **トレードオフ・仕様判断**: 段階1〜2で洗い出した「あえてこうした」判断とその根拠（処理順序、設計の非対称、あえて対応しなかった既知リスク、選んだ実装と退けた選択肢）
- **影響範囲・確認したこと**: lint/build/test 結果、動作確認、壊れていないことを確認した範囲
- **末尾**: `🤖 Generated with [Claude Code](https://claude.com/claude-code)` を記載

## 段階5: 先回り再確認 → 追加コミット or 終了

最後に、**作成したコミットと PR が「レビュー指摘に先回りできているか」を一段引いて再確認**する:

- 段階2で挙げた「質問されそうな点」が、すべてコメント or PR 本文で答えられているか
- コミットメッセージが「何を・なぜ」を説明し、レビューアが diff を読む前に意図を掴めるか
- 明文化すべき判断（段階1）で本文/コメントに反映し漏れたものはないか

問題があれば **追加コミット**（コメント追記・PR 本文修正含む）。問題なければ **終了**。

## 出力

最終的に以下の形式でまとめて報告する:

- **各段階の結果**（通過 / やり直した回数と理由）
- **must（マージ前に直すべき）**: バグ・規約違反・型不整合など（すべて解消済みであること）
- **nice-to-have（任意改善）**: 各項目に自分の推奨（直す/現状維持）と理由を添える
- **PR 本文に明記した判断**: トレードオフ・仕様判断のサマリ
- **lint / build / test 結果**

指摘が新種のパターンで、今後も繰り返しそうなら `.claude/feedback/log.md` への追記も提案すること。
