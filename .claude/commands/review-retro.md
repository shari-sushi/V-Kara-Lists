# レビュー指摘の振り返り（review-retro）

`self-review` が「指摘が来る前の予防」なのに対し、これは **実際に来たレビュー指摘を起点に学習ループを閉じる事後フェーズ**。
目的は「同じ種類の指摘を二度受けないようにする」こと。そのために、各指摘について

- **修正が必要な指摘** → なぜ自分のセルフレビューで気づけなかったかを突き止め、次回のチェック観点にする
- **疑問・修正不要の指摘** → なぜレビューアにそれを言わせてしまったか（＝事前明文化の漏れ）を突き止め、**今この場で** PR 本文／コードコメントに先回りで書く
- **コメントと実装のズレ** → どちらが正かを確定して直し、なぜセルフレビューの照合をすり抜けたかを記録する

を行い、最終的に `.claude/feedback/log.md`（必要なら `lessons.md`／`self-review.md`）へ反映する。

対象指摘・補足: $ARGUMENTS

## 進め方

### 1. 指摘を集める

引数に応じて入力を確定する。

- **PR 番号が与えられた／省略された場合**: 現在ブランチの PR を特定し、レビューを取得する。
  - `gh pr view --json number,title,url,body` で PR を特定
  - `gh pr view <N> --comments` で会話コメント
  - レビュースレッド（行コメント）も拾う: `gh api repos/{owner}/{repo}/pulls/<N>/comments --jq '.[] | {path, line, body}'`
  - 別セッションのセルフレビュー結果など、チャットに貼られた指摘も対象に含める
- **指摘テキストが貼られた場合**: それをそのまま対象にする。

各指摘を「1指摘=1項目」に分解して列挙する（1コメントに複数論点があれば分ける）。

### 2. 対象の差分・文脈を把握する

- `git --no-pager diff develop...HEAD`（または PR の base）で、指摘箇所の実コードを必ず開く
- 指摘が「思い込み」か「実バグ」かを判定するため、**指摘対象のコードと、その周辺（同一ファイルの隣接関数・呼び出し元・データ源の API 契約）まで読む**
  - 教訓: 過去の見逃しは「diff 内部の論理は見たが diff の外（API 契約・隣接関数）を見なかった」型が多い

### 3. 各指摘をトリアージ（3分類）

| 分類 | 定義 | この後の対応（§4） |
| --- | --- | --- |
| **A. 要修正** | 実バグ・規約違反・型/値の不整合など、直すべきもの | 修正する＋「セルフレビューで気づけた経路」を特定 |
| **B. 疑問・修正不要** | レビューアの質問、または実装時に検討済みで妥当なトレードオフ。コード変更は不要 | **先回り明文化**（PR 本文 or コードコメント）を今書く |
| **C. コメント／ドキュメントと実装のズレ** | 実害は無いが、コメント・型注釈・PR 説明が実コードと食い違う | どちらが正かを確定して直す |

判定に迷うものは A 扱い（安全側）。B と決めるのは「実コードを読んで妥当性を裏取りできた」ときだけ。

### 4. 原因調査と対応

各指摘について、**「なぜ事前に防げなかったか」を一次原因まで掘る**。表面の事象ではなく、セルフレビューの観点やプロセスのどこが抜けたかを言語化する。

#### A. 要修正

1. 修正を実施（または修正方針を提示）。
2. **「セルフレビューで気づけたか」を判定する**:
   - 気づけたはず → どのチェック観点なら拾えたかを特定。その観点が `self-review.md` のチェックリストに**無ければ追記を提案**、**有るのに素通りしたなら**なぜ素通りしたかを記録。
   - 構造的に気づけない（実機でしか出ない等）→ 検証手段（テスト追加・動作確認 等）の不足として記録。

#### B. 疑問・修正不要

1. **今この場で先回り明文化する**（これが本コマンドの肝）:
   - レビューアが「なぜこうなっているか」を尋ねた／settled な判断を再指摘した、ということは **その根拠がコード／PR から読み取れなかった** ということ。
   - 根拠を **コードコメント**（その判断が宿る行の近く）または **PR 本文**に追記する。提案ではなく実際に編集する（`Edit` / `gh pr edit --body-file`）。
   - 既存教訓の「再指摘されやすい3類型」を特に意識する: (a) 1往復に畳めるのにあえて畳まない、(b) 一見冗長な型アサーション、(c) 既存別ファイルの流儀に合わせた。
2. 原因は基本的に **「事前明文化の漏れ」**。`self-review.md` の明文化チェックが機能しなかった理由を記録する。

#### C. コメント／ドキュメントと実装のズレ

1. **実コードを正として**、どちらが正しいかを確定（コメントが嘘か、実装がバグか）。コメントが嘘ならコメントを直す。実装がバグなら A に再分類。
2. 既存の頻出パターン: コメント中の具体値（クラス名・数値・カラム名）が実値と不一致／コメントが隣接関数・外部APIの挙動を誤って引用。
3. 原因は **「コメントを散文として読み流し、コード本文との値照合を独立項目として通さなかった」**。これを記録する。

### 5. フィードバックを書いてループを閉じる

`.claude/rules/feedback.md` の運用に従う。

1. **`.claude/feedback/log.md` に追記**（append-only。既存エントリは編集しない）。各指摘につき1エントリ、形式は feedback.md のテンプレートに合わせる。日付は会話中の「今日の日付」を絶対日付で書く。
2. **同一カテゴリが log.md に3件以上**たまったら、`.claude/feedback/lessons.md` にパターンを蒸留し、該当エントリに `[distilled]` を付ける。
3. **`self-review.md` のチェックリスト更新提案**: §4-A/§4-B で「この観点があれば次回拾えた」と特定したら、`self-review.md` のチェックリストに項目を足す差分を提案する（ユーザー承認の上で編集）。これが「次回はセルフレビューで気づける」を実現する最重要ステップ。

## 出力

最後に以下をまとめる:

- **指摘一覧（トリアージ済み）**: 各指摘を A/B/C で分類し、一次原因を1行で
- **実施した修正**（A）／**先回り明文化した箇所**（B: PR 本文 or どのコメント）／**直したズレ**（C）
- **log.md に追記したエントリ**（タイトルとカテゴリ）
- **self-review.md / lessons.md への反映提案**（あれば差分案）

## 注意

- **B を「脳内で納得して終わり」にしない**。納得した根拠を外（コード/PR）に出すまでが対応。出さなければ次のレビューアがまた同じ質問をする。
- **A を「直して終わり」にしない**。直すのは当然で、価値は「次回セルフレビューで先に気づく観点を1つ増やす」こと。
- log.md への記録時、**実害が無くても省略しない**（ズレ・疑問も将来の蒸留材料になる）。
