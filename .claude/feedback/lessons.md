## design

- **module-level の可変状態を置いたら、アイデンティティ変更（ログアウト/ログイン）・マルチタブの観点で寿命を評価する** — 「リロードせず再訪しても保たれる利点」は、裏返すと「ユーザーA→ユーザーB 切替で前ユーザーの状態が残る危険」。便利＝残る、と評価した時点で危険＝残るの両面を点検する。
- **共有 state を新たに上書き／再取得する変更を入れたら、その state を書く他の経路を全列挙して競合を点検する** — fetch 対 fetch だけでなく、楽観更新・fire-and-forget の保存・別 effect/別ハンドラといった「もう一方の書き手」との競合（未確定の書き込みを後着が潰す等）まで脅威モデルに入れる。
- **共有関数に副作用（書き込み・ヘッダ・グローバル state 変更）を新規に足したら、同じリソースを書く他経路と同一レスポンス/トランザクション内の write 競合を点検する** — 特に失効・リセット系（logout/delete/expire）は延長・更新系と必ずぶつかる。最優先で照合する。

## code-quality

- **コメントの主張は、参照先のコードを開いて裏取りしてから書く** — 「○○と同種」「××で防止」等で他の挙動に言及するなら、外部API・認証フローだけでなく**同一ファイル内の隣接関数**も対象に開いて確認する。引用元を読まず思い込みで書くと実挙動と食い違う。「直す対象」と同じ検証を「直した結果」にも適用する。
- **コメント中の具体値はコードからコピペで一致させる。値に言及不要なら数値を書かない** — クラス名・数値・しきい値・カラム名に言及するなら実値と1文字単位で一致させる。「同種」「程度」の曖昧語で逃げても、引き合いに出す対象の値は開いて照合する。そもそも陳腐化する具体値（サイズ・透過度等）はコメントに書かない方が安全。
- **コメントとコードのギャップは「正確化」ではなく「抽象化」で潰す** — 具体値・breakpoint 差・しきい値を列挙するほど、片方の変更で陳腐化する。メカニズムの本質だけ残し、クラス値が変わってもコメントが真のままになる粒度まで上げる。ギャップを「軽微」と格下げして許容しない。
- **差分の正しさだけでなく、既存パターンとの一貫性を確認する** — 同種の処理が既にあるなら、その流儀（エラーハンドリング・型定義の置き場所・deps の作り方・3層アーキの責務分離等）に揃っているか照合する。自分の差分内の論理が正しくても、既存の流儀とズレると不整合になる。
- **同じ不変条件を2箇所以上に手書きコピーしたらヘルパーへ集約する** — 非自明な不変条件（「より広いときだけ適用」等）が複数箇所に現れたら共有化する。自分の修正で既存ロジックを手書きコピーしていないか、「直した結果」にも一貫性 lens を当てる。
- **「後で回復/再取得される」の主張は、その再実行トリガが実在するか裏取りする** — 握りつぶしやコメントの根拠に「次の○○で再取得される」と書くなら、その再実行を起こす具体的トリガ（どの dep 変化・どのイベント）が実在するか確認する。安定参照の deps では effect は自発再実行しない。

## architecture

- **新しいエンドポイント/ハンドラは「正しい peer ファミリ」の横断ガードを全部引き継ぐ** — (1) まず比較対象を**同じ actor／認証モデルの peer**に正す（たまたま開いた“似た”兄弟の形を踏襲しない）。(2) その peer ファミリが一律で持つ横断的な認可ガード（認証チェック・所有者保護・利用停止チェック等）を全部引き継いだか列挙して照合する。(3) **ガードを省くなら意図的に**——省略には理由コメントを必ず添える（無言の欠落は authz バイパスになる）。

## ux

- **状態遷移を伴う操作は「操作後の画面変化をユーザーが事前に予測できるか」を1観点として評価する** — データの正しさ（再取得で整合を取る等）を潰しても、表示が大きく変わる/消えるトグルは利用者を不安にさせる。その場に副作用の一文（安心材料込み）を添える。

## process

- **検討済みの判断は「採らなかった代替案＋却下理由」まで PR/コメントに先回りで書く** — 自分で妥当と判断したトレードオフ（処理順序・設計の非対称・一見冗長な型アサーション・既存別ファイルの流儀踏襲・中核関数への副作用追加など）は、根拠が PR/コードから読めないとレビューアが必ず再指摘 or 代替案提示してくる（往復コスト）。明文化チェックの合格基準は「**制約**を書いたか」ではなく「**この設計を見たレビューアが思いつく代替案を、却下理由つきで先回りしているか**」。レビューアが代替案を出してきたら、それは「なぜ採らなかったか」が PR から読めなかった証拠。「正しさの検証」と「再指摘されないための明文化」は別作業として独立に1パス回す。

## other

- **ユーザー制御の文字列を新しい外部シンクへ流したら、そのシンクの既定解釈を確認して安全側に明示設定し、敵対的入力テストを1件足す** — 外部シンク（SQL・HTML/テンプレート・シェル・ログ・メール・外部API本文等）はデフォルトで入力を「解釈」して副作用を起こすことがある。SQL は文字列連結せず GORM のプレースホルダ（`Where("col = ?", v)`）を使う。HTML は `dangerouslySetInnerHTML` 等の生注入を避ける。`name` や `note` のような“ただの表示文字列”でも、新規の送信/出力経路に埋め込むなら taint 源として扱う。`name="<script>..."` のような敵対的入力ケースをテストに入れる。**「既存コードに合わせる」一貫性 lens はここで逆効果になりうる**（既存が無防備でも、任意のユーザー入力を新たに埋める経路は危険度が違う）。
- **taint レビューのスコープは「diff の追加行」ではなく「触れた経路に流れる全入力」** — 新規シンク経路を足すついでに、同じ関数・同じヘルパーへ既に流れている近傍のユーザー入力も射程に入れて最悪値を当てる。「自分が足した行」だけ点検して既存の埋め込みを見落とすのが典型ミス。公開（public）出力は限定的（internal/認証済み）出力より危険度が高いので優先する。
